# Discord Prifiler — Сводный анализ (Багхантер → Аналитик → Архитектор)
Версия для AI-разработчика. Компактная. Все пути — от корня репозитория.

## 0. ЧТО ЭТО
Discord-бот «профайлер»: собирает сообщения/реакции участников, LLM строит психологические
профили (Big5/OCEAN), админка на Flask+HTMX показывает данные и управляет сбором.
Стек: Python 3.11, discord.py, Flask (app/admin), PostgreSQL (psycopg), SQLAlchemy-core SQL,
Alembic (объявлен, почти не используется), Docker Compose. Точек входа две: main.py (бот+коллектор),
admin_app.py (админка). Схема БД живёт в app/db/schema.sql + страховочных DDL в коде.

## 3. АНАЛИТИКА: СИЛЬНЫЕ СТОРОНЫ (не ломать)
- Resume-safe курсоры сбора (курсор хранится в БД, идемпотентная вставка).
- PG-триггеры агрегатов (счётчики сообщений/реакций пересчитываются на уровне БД).
- Data Quality Gate перед LLM-вызовом (мин-max объём текста, детальный учёт).
- Чистый MVC у коллектора; README описывает метрики хорошо.

## 4. АНАЛИТИКА: СИСТЕМНЫЕ ПРОБЛЕМЫ
- Разрыв контракта «код ↔ схема ↔ README»: колонки, которые код пишет, отсутствуют в схеме (§1.1).
- 0 (ноль) автотестов при 130+ коммитах → плодятся «страховочные» ALTER в рантайме вместо миграций.
- Монолит админки ~1600 строк в одном app.py: смешаны views, контекст, SQL-редактор, управление сбором.
- Приватность: сырые сообщения хранятся бессрочно, нет retention-политики и анонимизации экспорта.

## 5. АРХИТЕКТУРА: ЦЕЛЕВАЯ СТРУКТУРА
### 5.1 Админка
Разбить app.py на blueprints вокруг ЕДИНОГО AdminContext (app/admin/bp/*):
- `core.py` — контекст, view-columns, права;
- `views.py` — чтение/таблицы; `collect.py` — управление сбором; `analysis.py` — LLM-операции;
- `sql_lab.py` — изолированный read-only редактор.
### 5.2 Фоновые задачи — универсальная таблица `bg_jobs`
Паттерн уже есть в проекте (pending_dm). Обобщить: id, kind, payload jsonb, status(pending|running|done|error),
attempts, last_error, created/updated. Все долгие операции (LLM-анализ, полные ресканы, экспорт) = enqueue +
worker-цикл. HTTP-эндпоинты только ставят в очередь и показывают статус (HTMX poll).
### 5.3 Схема БД — единственный источник = Alembic
- Перенести весь ensure_schema-DDL в миграции; страховочные рантайм-ALTER удалить ПОСЛЕ зелёного CI с тестом
  `alembic upgrade head` на чистой БД.
- Добавить недостающие колонки (§1.1) честной миграцией.
### 5.4 Конфигурация
pydantic-settings: один модуль config.py, валидация env на старте, секреты не в коде.
### 5.5 Процессы
Две systemd/Docker-единицы: bot-collector (main.py) и admin (gunicorn, workers=1+threads или 2w sticky-нет).
Обмен — только через PostgreSQL. Redis опционально позже для очереди.
